The split is deliberate. Physics lives in Dyad, where the acausal connections and unit checking help. Algorithms that are not equations — a QP solver, a path planner, a bisection search — live in Julia. The plant never needs the reference path; only the controller and the scorer do.

The tyre sets everything else

Magic Formula lateral force with load-sensitive friction and a friction-ellipse derating for combined slip:

# dyad/tire.dyad
F_z_pos = 0.5*(F_z + sqrt(F_z^2 + F_z_eps^2))
mu      = mu0*(1 - k_mu*(F_z_pos/F_z_nom - 1))
D       = mu*F_z_pos
phi     = B*alpha - E*(B*alpha - atan(B*alpha))
F_y_pure = -D*sin(C*atan(phi))
e_x     = F_x/D
g_ell   = sqrt(0.5*((1-e_x^2) + sqrt((1-e_x^2)^2 + eps^2)))
F_y     = g_ell*F_y_pure

Every formulation choice here is about the solver seeing something smooth: a rectified F_z so wheel lift cannot go negative, and a smoothed square root so the ellipse collapses gracefully instead of going imaginary.

k_mu is not decoration. With D = μ·F_z strictly linear in load, two tyres at F_z/2 are exactly one tyre at F_z — a double-track model would then be algebraically identical to a bicycle. Load sensitivity is what makes lateral load transfer cost grip at all.

Tyre characteristic

Two vehicles, one base

partial component PlanarVehicleBase
// the three degrees of freedom

// trajectory, for plotting

VehicleBicycle3DOF adds two WheelStations, VehicleDoubleTrack3DOF adds four. Both use the same station component, so corner physics is identical and the only structural difference is lateral load transfer and track-width yaw moment.

Why a lag on load transfer? Quasi-static transfer makes Fz depend on ay, which depends on Fy, which depends on Fz — a nonlinear algebraic loop. A first-order suspension lag (τ ≈ 0.05 s) breaks it and is the physical reason roll is not instantaneous. The result is a pure ODE: no algebraic states.

Step steer: where the bicycle stops being enough

Why they diverge

1. Axle capacity loss

Transfer ±Δ across an axle carrying F, on a degressive tyre:

D₁ + D₂ = μ₀·F·(1 − 4·k_mu·Δ²/F²)

The loss is quadratic in transfer and strictly negative. No retuning of a bicycle model reproduces it, because a bicycle has no Δ.

2. Limit balance

eps_f, the front share of roll moment, decides which axle saturates first. Sweeping it reproduces the classic rule exactly:

The bicycle is not merely optimistic, it is qualitatively wrong here. It gives up ~6 % more ay than it should at 0.8 g, and then goes unstable where the real car is comfortable — because with no lateral transfer its limit margin between axles is only 2 %, so a step input tips it into oversteer.

Knowing where a model stops being valid

The slip angle is regularised so it stays smooth and bounded at standstill:

alpha = atan(vy_t / sqrt(vx_t^2 + v_eps^2))

The denominator is strictly positive, which is what keeps the model well-behaved at low speed — but it also means the tyre always believes it is rolling forwards.

This was found, not assumed. An eps_f = 0.35 run spun, reversed, and reported ay = 1.52 m/s² at a sampled time — a perfectly plausible-looking number produced entirely outside the model's validity envelope. The vehicle was travelling at −8.4 m/s.
// dyad/vehicle.dyad — PlanarVehicleBase
"Validity envelope: the regularised slip-angle definition assumes
 forward motion, so results are meaningless in reverse"
assert vx > -v_eps

The solve now halts at the boundary and returns Unstable rather than producing confident nonsense. A model that cannot say when it is out of range is more dangerous than one that is simply coarse.

Closing the loop: a double lane change

Dyad holds the plant

component DLCPlantDoubleTrack
  car = VehicleDoubleTrack3DOF(vx0 = vx0)
  act = DriverActuator(vx_target = vx0, ...)
relations
  act.vx_meas = car.vx
  car.Fx_req  = act.Fx
  car.delta   = act.delta

act.delta_cmd is a free parameter with no binding, so the controller writes it at every sample instant; the first-order steering actuator then supplies the hold dynamics a real steering system would.

Julia holds the controller

A QP solver cannot be written as Dyad relations, and the plant does not need the reference path — only the controller and the pass/fail scorer do.

# genuine sampled-data control, ZOH at 50 Hz
while integ.t < T
    z0 = [vy, r, e_y, e_psi, delta]
    Dseq .= kappa_ref.(path, X .+ vx.*k.*Ts)
    solve_qp!(U, qp, z0, Dseq, u_prev)
    integ.ps[P.act.delta_cmd] = U[1]
    step!(integ, Ts, true)
end
Protocol: constant speed. A speed-hold PI fights cornering drag, so the manoeuvre is a pure lateral-grip limit with no longitudinal load transfer helping the front axle. Harsher than the ISO coast-down protocol.

The mistake that mattered most

My first reference was a smoothstep centreline that snaps from lane to lane. It is curvature-continuous and looks entirely reasonable — and it is infeasible.

Referencemin radiusay at 25 m/sverdict
smoothstep centreline44.5 m14.0 m/s² beyond any tyre
minimum-curvature through the corridors115 m 5.4 m/s²feasible
Why: the gates are wider than the car, so a real driver cuts corners and uses the whole corridor. A centreline throws that away. The difference is a factor 2.6 in required lateral acceleration — about 1.6× in achievable speed. Tracking the wrong reference would have measured the planner, not the car.

The fix is a planner, not a formula: minimise the discrete ∑(y″)² subject to corridor boxes. That is a box-constrained QP, solved exactly by an active-set loop — solve equality-constrained, pin the worst violator, repeat.

ISO 3888-2 is infeasible for this car and the code says so rather than returning a kinked path. At moose-test widths a 1.76 m body leaves the CG a negative margin in gate 3. The symptom when I first ignored it was κ = 0.59 (R = 1.7 m); reference() now raises an error instead.

The MPC driver

Prediction on path-relative error dynamics, derived directly from the plant's own tyre sign conventions, with δ as a state so the controller models the actuator it drives:

z = [vy, r, e_y, e_psi, delta]
u = delta_cmd       d = kappa_ref
  • Exact ZOH discretisation, Ts = 20 ms
  • Condensed over N = 100 (2.0 s = 65 m of preview at the limit)
  • Curvature preview — the controller sees the path ahead, which is the whole reason to use MPC here rather than pure feedback
  • Input box constraint |δ| ≤ δmax; δ-rate penalised
  • Prediction model re-linearised at the operating point (LTV)

Tuning weights and horizon independently would have left 0.9 % of the speed on the table.

The solver had to be replaced

Condensing over 50 steps leaves cond(H) ≈ 5×10³. Projected coordinate descent, the obvious cheap choice, does not converge:

methodobjectivevs optimum
coordinate descent, 80 sweeps−26.21+11 %
active set (direct solve)−29.3876exact

With no constraint even active. The problem is only 50×50, so a direct solve is both exact and cheap; the active set pins the worst violator, then releases any bound whose gradient points back inside.

KKT residuals at machine precision across 0, 27, 44, 48 and 50 active constraints — including the all-pinned case, which an earlier version returned without ever checking.

The driver is not the bottleneck

Which is what "reach the highest possible speed" actually demands. Sweeping the MPC weights and horizon, each configuration re-optimised over the planner inset, moves the bisected speed by under 3 % — a 16× range on tracking weight, a 6× range on the rate penalty, horizons from 0.6 s to 1.6 s. The limit belongs to the vehicle and the course.

But that insensitivity hid a real fault. Max speed cannot see steering quality: the car stays in the corridor whether the wheel moves smoothly or thrashes. Tuning on speed alone left a cost function that spent ±110° of steering to chase millimetres. See the next slide.

Pass criterion

  • All four body corners inside the corridor — cones are struck by bodywork, not by the centre of gravity
  • No spin (|β| < 20°)
  • Run stays inside the model's forward-motion validity envelope
  • Entry speed bisected to 0.05 m/s, with both brackets checked
The planner inset is part of the driver: it trades corridor margin against path curvature, both monotone and opposed, so there is an interior optimum. Reporting any single inset would understate the car.

Diagnosing a steering trace that looked wrong

The commanded steering was oscillatory and visibly larger than the path needs. Four hypotheses, eliminated in order — each test designed so a negative result was as informative as a positive one.

HypothesisTestResult
Rough reference curvature swap the kinked QP reference for a C² analytic one not the cause — 3× lower peak steering rate, but the oscillation stayed
Tyre saturation / model mismatch sweep speed from 22 % to 94 % grip not the cause — oscillation present at 22 % grip too
Penalising yaw rate r instead of yaw-rate error set q_r = 0.3, 0.1, 0 not the cause — curves essentially identical
Finite horizon, no terminal cost horizon 1 s → 7 s not the cause — all horizons give the same curve
Badly scaled cost check condensing and objective against explicit evaluation both exact (2×10⁻¹⁶) — so the ugly trace was the true optimum
Root cause. With q_ey = 48 per m² and R = 0.5 per rad², a 0.1 m lateral error costs 0.48 while a 0.1 rad steering input costs 0.005 — steering was ~100× cheaper than error. The optimiser did exactly what it was asked: spend unlimited steering to drive the error to millimetres. Nothing was broken; the question was wrong.

Fix 1 — scale the cost

R = 50 balances a 0.1 m error against a 2.5° road-wheel input. Peak steering 109° → 66°, rms rate 389 → 183 deg/s, speed unchanged.

Fix 2 — re-linearise (LTV)

At 31 m/s the real secant stiffness is 0.50 of nominal at the front and 0.25 at the rear, so the MPC believed the car four times more responsive than it is. Re-linearising at the operating point cut tracking error 75 → 28 mm and raised the limit from 31.7 to 32.5 m/s.

What this model is not

Structural limits

  • Three degrees of freedom. No roll, pitch, heave or suspension travel. Load transfer is quasi-static with a lag. Body attitude in the 3D views is a reconstruction, not a state.
  • No wheel-spin dynamics. Longitudinal force is commanded; combined slip is handled by the friction ellipse. ABS or traction control would need 4 more states.
  • Forward motion only, enforced by assertion.
  • No steering column. The steering-wheel angle is a 16:1 readout.

Choices worth challenging

  • Gate geometry is parameterised, not certified. Defaults approximate ISO 3888-1; I deliberately did not assert standard dimensions from memory.
  • Understeer comes from a per-axle stiffness split (Bf = 8, Br = 10, giving 0.83 deg/g). With identical tyres the model is nearly neutral, because load sensitivity alone almost exactly cancels the weight distribution — real understeer comes mostly from suspension kinematics this model does not have, so it is lumped into the axle characteristic.
  • Reported speeds depend on the planner inset, which is optimised over. It is the best this driver achieves, not a certified ISO result.
  • Cones are discrete at 3 m, so a shallow incursion between two cones is a negative margin with no cone struck. The margin plot is the strict test.
